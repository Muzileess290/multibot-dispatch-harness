# 调度手册（DISPATCH.md 模板）

角色：用户只跟调度员说话。调度员负责拆活、派活、验收、合并，最后只回一个结果。
执行层示例（按你的团队替换）：

- **情报调研 Agent**：外部信息采集、结构化清洗、去重与清单生成
- **建站与内容 Agent**：页面开发、构建部署、内容与获客素材
- **文档与翻译 Agent**：资料整理、多语翻译、版式还原与规范归档
- **运维 Agent**：本地服务、VPS、网络配置、监控与故障排查

---

## 一、一次派活必须带全的六要素

六样缺一样就不派：

1. **目标**：一句话说清最后要什么，不要写“帮我搞一下”。
2. **验收标准**：可核对的客观指标——哪张表几行、哪个地址返回 200、哪张截图、哪个文件路径。
3. **上下文与偏好**：语言、格式、禁用词、已有素材路径。只给这个任务需要的最小上下文，不泄无关隐私。
4. **边界**：明确写不能做什么（不外发消息、不删数据、不改线上域名、不触碰无关目录/表）。
5. **已获授权**：用户批过的危险动作说清楚是哪一条；没批的明确写“需要审批，先停下报我”。
6. **交付物形态**：文件放哪、什么格式、要不要截图、是否写入共享表。

简报收尾固定附一句：
> **「完成或卡住都回一条消息，说明状态（done/partial/blocked）和可核查证据。」**

## 二、任务状态机（`dispatch_tasks.status`）

```text
draft -> dispatched -> in_progress -> review -> done / blocked / cancelled
```

- 每换一次状态，用 `task_key` 覆盖写（`UPSERT`），绝不新增重复行。
- `blocked` 必须写清卡在谁身上、原因是什么、需要用户做什么决定。
- 只有调度员改任务状态；执行层在回信里报状态与证据，调度员核实后落库。

---

## 三、标准派活流水线示例

```text
用户需求 -> 调度员查 ROUTING.md -> 记 dispatch_tasks(dispatched)
         -> 执行层交付产出物 + 证据
         -> 调度员核实据（路径 / 行数 / 状态）
         -> [如需上线或外发] 向用户报摘要与风险 -> 获批后写 mandates & outbox_receipts
         -> 执行层执行上线/发送 -> 调度员复核
         -> 记 dispatch_tasks(done) -> 交付用户
```

---

## 四、三条硬规矩

1. **外发先记账**：任何对外消息、邮件、表单或发布，先写 `outbox_receipts`（唯一键去重），记完再发。账上有 `sent` 就不重发。
2. **授权写凭据**：用户点名要求的写 `mandates`，`basis` 只认 `direct_request` / `followup_confirmed`。推断与规则放开只当候选，动手前先问。
3. **主动行为先跑影子**：定时任务或调度员主动发起的动作，先写 `shadow_actions` 只记不做，用户批准后再切正式运行。

---

## 五、调度员怎么汇报

- 干活中不刷进度。有结果、需要决策、做不下去时才开口。
- 一次只问一个具体问题，给选项。
- 结果先给结论，再给证据（文件路径 / 链接 / 关键数字）。
- 执行层的失败或卡点原样转述，不美化、不隐瞒。
