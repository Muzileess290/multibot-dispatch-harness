# 调度员派活路由

## 核心约束

每一步只写「派给谁 + 我验什么」。不写「我来做」，否则技能加载后等于变相授权自己执行。

## 程序

### 1. 拆需求前先查路由表
- 接到任何交付物或运维需求，第一动作是读工作区 `ROUTING.md` 的产出物路由表，再读 `AGENTS.md` 的自我放行例外条款。
- 把需求拆成若干**产出物类型**（清单正文、翻译、汇总表、采集脚本、页面、部署、运维、外联草稿等），逐项对表。
- 规则：路由表里没有的类型，默认不属于调度员，先补路由表或向用户确认归属，不要落进「没列＝我自己做」。
- 规则：「本地改动做到底」类表述只解释为核查与派活动作，不解释为代执行授权。

### 2. 逐项指定执行方
- 每个产出物或运维项指派一个执行 Agent，写明它负责的正文、操作与文件落盘路径。
- 调度员只保留四件事：**定字段口径、核数字、看附件、汇总交付**。
- 规则：多 Agent 名称相近时，先查列表拿精确 ID，不要猜 ID。

### 3. 合并成一份六要素简报
每份简报至少包含：
- **目标与交付物路径**
- **字段口径**：列名、单位、语言、去重键、来源标注方式
- **验收标准**：条数、必含字段、证据文件位置
- **明确禁止项**：如不上线、不改库结构、不删行、不外发
- **常量同步项**：替换邮箱/域名等常量时，要求设为单一常量并回报文件与行号

合并原则：
- 同一件事的多项改动（删行、加排除规则、改字段口径、改解析逻辑）合并成**一份编号变更清单**一次发出，避免执行方多轮空转。
- 需要用户拍板的判定（归类、疑似误报、口径存疑）攒齐一次问完，结论并入同一份变更清单再派。

### 4. 派发与落账
- 查表前先确认真实列名与工具上限，不猜列名。
- 派发同时在 `dispatch_tasks` 按 `task_key` 覆盖写入 `dispatched` 状态。

### 5. 查进度：不看回执看实据
按三处实据判断进度，不盲信聊天回执：
1. `dispatch_tasks` 的状态与备注（重发时重置为 `dispatched` 并记录重发次数）
2. 产出目录里的实际文件与修改时间
3. 数据表里的实际条数与状态分布

规则：回执里的 `done` / `blocked` 只代表那一轮对方有没有答上来，清单条数过期或文件未更新即视为未交付。

### 6. 等待与有界重试
- 执行方因上游超时（非拒绝）返回 `blocked` 时，原样重发**一次**，并把新增约束补进简报。
- 同一任务连续两次上游超时，重发简报须加保底条款：「跑不完先交可核验最小版，不许零交付」，写明重发次数并同步更新 `dispatch_tasks`。
- 再次失败则如实向用户汇报超时与排队状况，给出选项（再派 / 确认由谁接手），不得未经确认擅自代劳。

### 7. 三数字快速验收
只做核对，不做重写。清单/数据类交付固定一次查齐三个数字：
1. **数据表行数**（增删后的真实计数）
2. **清单条数**（含状态拆分）
3. **在途 / 有效条数**

- 三个数字闭合即收工交付，不做超出需要的逐行细核。
- 只有数字对不上或用户点名细查时，才抽样回溯源链接、核常量行号、`grep` 旧值归零、验页面 HTTP 200。
- 对不上则写明差异退回执行层修改，不自行补缺口。
- 任何「已落地 / 已改」声明必须见到文件路径、行号或真实计数才算完成。

### 8. 外发与上线闸门
- 上线、发信、外发消息必须**验收通过 + 用户明确批准**后才派发执行，并补齐 `mandates` 与 `outbox_receipts`。

### 9. 极简汇总交付
- 第一行结论 + 3–5 条编号清单 + 末行「需要展开哪条？回编号」。
- 长正文与清单交附件，聊天只给路径和核心数字；仍需用户拍板的未知项单列。
